# 收纳箱删除文件后自动刷新设计

## 背景

WPS 打开文档时会在同一目录创建临时缓存文件，关闭文档后再删除该文件。FeatherFence 的收纳箱会显示缓存文件，但文件被 WPS 删除后图标仍然保留；手动重载配置会重新扫描目录，随后图标消失。

根因位于目录通知解析：`ReadDirectoryChangesW` 已订阅文件名和目录名变化，但 `parse_notify_names` 只上报新增、修改和重命名后的名称，过滤了删除与重命名前名称。因此删除操作没有进入栅栏已有的延迟刷新链路。

## 目标

- 目录内文件或子目录被删除后，关联栅栏自动移除对应图标。
- 文件或子目录被移出、重命名时，旧条目自动消失，新条目按磁盘现状显示。
- 复用现有刷新合并机制，避免 WPS 等应用产生的连续目录事件导致 UI 消息风暴。
- 不干预或删除应用的临时文件，不增加后台轮询。

## 方案

扩展 `parse_notify_names` 的事件过滤范围，同时接受：

- `FILE_ACTION_ADDED`
- `FILE_ACTION_REMOVED`
- `FILE_ACTION_MODIFIED`
- `FILE_ACTION_RENAMED_OLD_NAME`
- `FILE_ACTION_RENAMED_NEW_NAME`

监听器仍只向调用方提供发生变化的名称集合，不引入新的事件类型接口。栅栏监听回调不依赖具体名称，而是调用现有 `RefreshSignal::post`。防抖计时器等待目录事件安静后，由 UI 线程重新扫描目录并重新渲染。这使最终显示以文件系统当前状态为准，也天然处理多事件合并、删除与重命名组合事件。

桌面快捷方式和下载监听也会收到删除名称，但其候选处理逻辑会检查路径是否仍存在，因此不会把已删除文件移动到收纳箱。现有去重与稳定性检查保持不变。

## 数据流

1. WPS 删除临时缓存文件。
2. `ReadDirectoryChangesW` 返回 `FILE_ACTION_REMOVED`。
3. `parse_notify_names` 保留该通知并调用对应目录的监听回调。
4. 栅栏的 `RefreshSignal` 合并短时间内的连续通知。
5. UI 线程重新执行 `refresh_entries`，从磁盘目录构建条目列表。
6. 已不存在的缓存文件不再渲染；页码与选中项沿用现有收敛逻辑。

## 错误处理

- 目录句柄失效、读取失败和监听器停止继续使用现有恢复与退出逻辑。
- 删除事件到达后若目录暂时无法读取，沿用当前 `refresh_entries` 行为；后续目录事件仍可再次触发刷新。
- `PostMessageW` 失败时继续使用现有取消排队状态的处理，避免刷新信号永久卡住。

## 测试

- 单元测试验证通知解析会保留 `FILE_ACTION_REMOVED`。
- 单元测试验证通知解析会保留 `FILE_ACTION_RENAMED_OLD_NAME`。
- 目录监听集成测试验证已创建文件被删除时会收到该文件名通知。
- 运行现有测试，确认新增、修改、重命名后名称以及监听器停止行为没有回归。
- 构建 release 或执行 `cargo check`，确认 Windows API 常量导入和编译通过。

## 非目标

- 不为每种应用临时文件名增加特殊过滤规则。
- 不改为周期性扫描目录。
- 不实现按单个事件增量修改 UI 条目。
- 不改变收纳箱、文件夹栅栏、桌面快捷方式或下载自动收纳的业务规则。
